# Bounded public hub telemetry

## Audit

Read-only production inspection on 2026-10-19 found 37 rows in
`public.hub_activity_events`, owner-only SELECT RLS and public INSERT RLS checking
publication only. API roles had all table grants (including TRUNCATE, which RLS
does not filter). Allowed event names already numbered seven, source was arbitrary
text up to 40 characters, and a caller could choose UUIDs and created_at. No live
function consumed this table. The frontend directly inserted browser-generated
events and used a single localStorage device ID. Dashboard save counts combined
install_accepted and standalone_open by that ID; neither proves an installation.

## Launch implementation

`public.record_hub_activity(payload jsonb)` is a write-only SECURITY DEFINER SQL
wrapper, callable only by anon/authenticated, invoking owner-only private
`close_relax_private.ingest_hub_activity(jsonb)`. Both have empty search paths.
No API role can directly execute the private function. No Edge Function, new
table, secret, CAPTCHA, IP collection or scheduler is introduced.

The migration removes only public INSERT RLS for this table, revokes all PUBLIC,
anon/authenticated table/column rights, then restores authenticated SELECT subject
to the unchanged owner-only SELECT policy. It removes TRUNCATE/UPDATE/DELETE as
well as INSERT. Trusted service_role administrative privileges are unchanged.
Existing profile/public-hub RLS, plan enforcement and vendor behavior are untouched.

Payload must be an object of at most 512 serialized bytes with exactly four string
fields: profile_id (canonical UUID versions 1–5), device_id (canonical UUIDv4),
event_type and source. The event/source pairs are restricted:

- hub_view → public_hub
- standalone_open → installed_hub
- save_click, install_accepted, ios_instructions → main_button or floating_button
- savings_vivint_click, savings_goosehead_click → homeowner_savings

All other fields (including timestamps, names, email or arbitrary metadata) and
unknown values are rejected. ID and timestamp are generated by the server. The
profile must exist, be published and have a slug; request Origin must equal its
exact HTTPS hub origin. A profile row share lock excludes concurrent unpublication
until ingestion ends. Returns only true/false, never rows or profile details.

Origin is only a consistency check. Non-browser attackers can forge Origin and
device IDs. This does not establish homeowner identity or prove real engagement.
Other published hubs are intentionally eligible for anonymous tracking when the
request targets that hub. Neither an ID nor this endpoint gives cross-owner reads,
updates or private profile access. Metrics must not authorize access, billing,
rewards, commissions, or payments.

## Limits and retention

An immediate per-profile advisory transaction lock serializes writes; a busy hub
drops telemetry instead of building a queue. All time windows use server time:

- One event per profile/device/event type in a rolling five minutes, across sources.
- Maximum 30 recorded events per profile/device in a rolling hour.
- Maximum 500 recorded events per profile in a rolling 24 hours, across all IDs.
- Maximum 5,000 stored events per profile. Rotation of client IDs cannot bypass
  the profile caps. Existing over-cap history is not truncated by migration;
  new events stop until retention/admin pruning creates space.

Once valid ingestion passes dedupe/rate checks, records for that hub older than
90 days are pruned before the storage-cap check. No rows are deleted at migration
application. Dormant hubs do not receive automatic pruning. Recommend a daily
administrator/service-only retention pass deleting rows older than 90 days;
review/approve scheduling separately. Manual equivalent, for an authorized admin:

```sql
DELETE FROM public.hub_activity_events WHERE created_at < now() - interval '90 days';
```

Dashboard reads only the last 90 days, up to 5,000 newest records (a lower Data API
row limit can further reduce the sample). It now labels Browser IDs / Save Signals
and explains dedupe, caps and approximate counts. Browser IDs are now stored under
`closeandrelax-device-id-<profile UUID>`, separating hubs; the old global key is not
read or copied. Existing history may count a returning browser again after this
change. No fingerprint, location, contact/insurance data or new PII is collected.
Blocked storage uses one in-memory ID per hub until reload. Private preview stops
before obtaining/storing a device ID or sending a request. Tracking errors are
silent and do not affect install prompts, Savings navigation or homeowner actions.

## Validation and production follow-up

Local PGlite tests execute the actual migration against an inspected-schema
fixture, covering all legitimate event types, publication/origin mismatches,
malformed UUIDs/shape/extra fields, dedupe, device/hour and rotated-ID profile/day
caps, retained-row caps, expiration, direct DML denial, owner-only reads and private
function grants. Client tests check allowlisted payloads, failed network behavior,
preview suppression and per-hub device storage. Single-connection tests do not
exercise real multi-session advisory contention; verify that separately in staging.

After approval, apply `20261019183523_restrict_hub_activity_ingestion.sql` and
release the matching frontend together. Old clients' direct INSERTs will fail
quietly after migration; the hub remains usable, but those events are not saved.
No Edge deployment or secrets are needed. Recheck publication, owner isolation and
advisor output after application. Request-volume/DDoS protection is outside this
row-bounding RPC; add gateway/WAF controls if real abuse requires it. Saturation
can suppress legitimate signals, so retain approximate wording and monitor caps.
No production writes, migration application, deployment or commit occurred here.
